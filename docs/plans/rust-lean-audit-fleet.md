## Effective wiring map

1. H `Control.lean:2330-2407` handles enrolment and relay poll/respond **before** ordinary user auth. These routes authenticate their own node/enrolment credentials.
2. User REST resolves the principal at H `Control.lean:2416-2419`. Managed collection/create, stop/resume, single-machine GET/DELETE and remote-nodes routes are handled at `4596-4748`. Only then does fallback `dispatchRemoteFleetAndRelayRoutes?` run at `5702-5707`.
3. **Route shadowing matters:** H `Control.lean:4714-4724` matches `GET /api/managed-machines/:id` before fallback. Consequently normal `GET .../settings`, `.../providers`, and `.../snapshots` are treated as machine IDs and return 404 unless such an ID exists. Their seemingly implemented GET branches at H `RemoteFleetAndRelay.lean:1071-1104,1126-1128` are not effective REST implementations. POST `/snapshots`, DELETE `/snapshots/:id`, POST `/:id/snapshot`, and MCP snapshot helpers remain reachable. Route ordering belongs to the owned wiring work.
4. H `Control.lean:2324-2327` calls `McpGateway.dispatchMcpToolCall` with scoped claims. That dispatcher derives a user from the caller mission (`McpGateway.lean:171-190`); it does not automatically apply every REST owner check.
5. H `RemoteDispatch.lean:1074-1195` is the shared mission job submit path; REST create calls it at H `Control.lean:3654-3684`, and MCP start at H `McpGateway.lean:488-537`. Startup actually calls reattachment at H `Control.lean:6465`, but reattachment only searches durable mission-run handles (`RemoteDispatch.lean:1201-1253`).
6. H `OrbNode/OrbNode/Server.lean:674-804` verifies scoped submit claims and writes a queued node job before returning 202; H `Runner.lean:1311-1491` chooses confined privd execution versus shared execution. The principal losses below occur in Core or its particular callers, not because scoped node verification is wholly absent.

### FLT-01 — P1 / D — Resources overview discloses other tenants' missions and usage

- **R:** `src/api/resources.rs:28-37,538-574` resolves the authenticated user's SQLite store; mission detail likewise at `1399-1408`.
- **H:** `Core/Control.lean:5723-5727` passes caller identity, but `Core/ResourcesAndSystem.lean:1250-1252` discards it for overview. `buildResourcesOverviewJson:334-357,450-484` queries global usage and live roots and emits title, project, mission IDs and costs without an owner/access predicate. The detail route at `1254-1257` is correctly guarded, so it does not protect overview.
- **Scenario:** Alice and Bob have unrelated root missions in the shared store; Bob GETs `/api/resources/overview?range=6h` and receives Alice's live mission card/title/project and attributed spend. No mission-ID guessing is required.
- **PR-sized fix:** make overview require a principal and constrain usage, roots, descendant aggregation and managed links to that principal's readable mission set before grouping. Preserve explicitly intended aggregate fleet capacity separately. Do not treat a global DB as the old per-user DB.
- **Confidence:** high. NEW privacy defect, independent of the owned compute-history sampler.

### FLT-02 — P1 / D — Snapshot creation/deletion bypass tenant and project authority

- **R:** `src/api/managed_machines.rs:1113-1183` resolves caller scope; `src/managed/snapshots.rs:184-186,491-500,602-628` enforces tenant/project visibility, source-machine owner and scoped deletion.
- **H:** schema `Core/RemoteFleetAndRelay.lean:735-737` has no owner/project. Helpers `871-929` have no principal. Reachable POST `/api/managed-machines/snapshots` at `1129-1135` takes any `machine_id`; DELETE `/snapshots/:id` at `1137-1139` deletes without ownership. MCP list/delete at `Core/McpGateway.lean:834-842` uses the same unscoped helpers. The guarded MCP machine-snapshot branch does not fix those alternate paths.
- **Scenario:** a member with another tenant's machine ID POSTs `/snapshots`; a member with a snapshot ID calls DELETE (or learns IDs through MCP list) and removes another tenant's local snapshot record / attempts provider deletion. Provider errors are ignored, so local record deletion alone is demonstrable from source. Do **not** assume shadowed REST GET `/snapshots` is reachable.
- **PR-sized fix:** persist owner+project on snapshots; enforce scoped source-machine access on all creation paths and scoped lookup before list/delete/provider effects. Treat legacy ownerless snapshots as unavailable until explicitly migrated. Share one scoped service across MCP and REST.
- **Confidence:** high. NEW security boundary; actual Boat snapshot endpoints, receipts and retention remain owned lifecycle work.

### FLT-03 — P1 / D — Durable-job routes ignore authenticated ownership

- **R:** `src/api/durable_jobs.rs:336-369,1473-1492,1713-1723` authorizes explicit owner or legacy mission access on reads and cancel.
- **H:** `Core/RemoteFleetAndRelay.lean:1262-1295` does not use `callerUserId`, `isAdmin` or mission authorization. List `937-961` is global; get and update accept any job ID. Shared dispatcher is reached after authentication, not after per-job authorization (`Core/Control.lean:5702-5707`).
- **Scenario:** Bob lists all jobs, learns Alice's mission/node/job IDs, and POSTs Alice's job's `/cancel` or `/force`, changing its durable row. Today this does not necessarily signal Alice's process (FLT-04); it is still unauthorized disclosure and mutation of Alice's job state.
- **PR-sized fix:** central job authorization based on durable owner plus authorized mission access; filter list before pagination, reject unknown/unauthorized IDs uniformly, and apply it to every mutation and future logs route. Do this before wiring actual node cancellation/force.
- **Confidence:** high. NEW, not VM reconciler work.

### FLT-04 — P1 / S,D — “Cancel/force succeeded” is not an execution receipt

- **R:** `src/api/durable_jobs_remote.rs:276-297` sends node cancel and refuses to infer termination from acceptance; `src/api/durable_jobs.rs:1721-1739` performs real remote/local cancellation. R `src/api/control/remote_jobs.rs:2363-2378` retains cancellation ownership during loss of contact.
- **H:** REST durable cancel/force (`Core/RemoteFleetAndRelay.lean:1287-1295`) only writes `cancelled`/`running`, returns `ok:true` even without a matched row, and never calls a node. Separately `Core/RemoteDispatch.lean:807-813` marks cancelled on any HTTP response, including failure status; poller `869-880` sets `cancelSent` **before** sending once and discards the result.
- **Scenario:** cancel a running build through `/api/durable-jobs/:id/cancel`: this REST handler returns a cancelled row without signalling the node. A `/force` row update cannot start a queued node job. Separately, the poller's one-shot cancellation attempt can fail without that observer retrying; do not generalize this to all mission cancellation paths—some callers do send node cancellation, and another caller/attempt may still stop the work.
- **PR-sized fix:** one durable cancellation-intent/reconciliation path: authorize, record requested/uncertain, send actual node operation, retry until terminal evidence, and expose confirmed versus unconfirmed outcomes.
