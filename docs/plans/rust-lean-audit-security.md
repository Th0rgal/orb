## Numbered SEC dossier

### SEC-01 — Critical / M,D — Device approval is not verified; grants are labelled biometric-approved anyway

**Category:** authentication/authorization bypass. **Evidence tier:** code-confirmed — source-derived (direct evidence of missing server signature check; no live exploit). **New**, outside the two running recovery plans.

- **R evidence:** `src/api/approvals.rs:210–248` consumes a stored challenge, checks expiry and exact method/path/body hash, rejects revoked/unrecognized devices, and verifies the signature; `:298–302` uses ECDSA P-256 SHA-256. `:694–744` identifies protected operations and operations that are always signed; `:764–837` is the enforcing middleware. `:111–143` loads the persisted mode/devices fail-closed on corrupt state.
- **L full path:** `Core/Control.lean:2416–2418,5694–5700` authenticates and passes only `isAdmin` to the secret/approval dispatcher. `Core/SecretAndApproval.lean:901–908` does not receive request headers. `:940–958` returns a challenge payload but does not store it. `:984–1072` executes batch approvals without a signature. `:1337–1353` directly approves privilege requests; `:656–697` sets `biometricSigned := true` on every created lease. No production `X-Paloma-Approval` verifier was found in the Lean tree (the Core header occurrence is CORS configuration, `Control.lean:1142`).
- **Failure scenario:** an attacker who obtains an admin bearer but not the enrolled hardware key can approve a pending `root_exec` request, approve cross-mission/secret access, or unbunker the fleet. The privileged verifier subsequently consumes a lease whose biometric bit was invented, not verified. This bypasses a deliberate second factor even for an otherwise authenticated admin.
- **One-PR fix:** add one fail-closed server middleware at the common protected-route boundary. Persist/consume bounded one-shot challenge state; bind method, normalized path, exact bytes, summary, device and expiry; verify enrolled nonrevoked P-256 keys; preserve `always_signed` semantics. Carry verified evidence to lease creation instead of setting `true`. Include negative cases for absent, replayed, changed-body, revoked-device, expired and wrong-path signatures and for direct/batch/alias routes. This PR is security containment; do not rebuild each broker separately.

### SEC-02 — High / D — Password-shaped bearer and unknown legacy JWT subjects acquire bootstrap-admin authority

**Category:** privilege/tenant identity escalation. **Evidence tier:** code-confirmed — source-derived (conditional on valid configured credential or legacy JWT).

- **R:** `src/api/auth.rs:507–541,624–629` authenticates a JWT. In **multi-user mode**, `:529–532,642–649` resolves the configured JWT subject (or the allowed GitHub identity). In **single-tenant mode**, `:533–536` accepts the valid JWT's original `sub`/`usr`; it does **not** always reject an unknown subject. Multi-user login requires username and returns that account (`:428–465`). Password authentication is not an alternate arbitrary API bearer.
- **L:** `Core/Control.lean:400–410,413–420` accepts any configured password as a bearer without naming a user. `:471–488` maps that Boolean to the bootstrap admin rather than the password's owner, without checking the password owner's disabled/session state. The `eyJ` path at `:447–470` maps an unknown subject to a bootstrap admin, or invents an admin if none exists. `Core/Store.lean:3646–3655` seeds every configured user as an admin, rather than preserving Rust's per-user store identity; demotion/disable does not remove the static verifier.
- **Failure scenario:** a configured account is disabled or demoted in `users`, but its unchanged static password is sent directly as `Authorization: Bearer ...`; it can authenticate as an enabled bootstrap admin. Separately, an unexpired pre-cutover JWT whose subject is not in the Lean database can be assigned bootstrap-admin identity instead of preserving its original valid single-tenant subject or applying the historical multi-user subject check. **Lean v2 live-user, disabled and session-epoch checks remain effective**; the finding concerns the additional raw-password/legacy fallback paths. This is not merely HTTP-01's ability to obtain a new token using an old password.
- **One-PR fix:** remove password-as-API-bearer authentication; resolve signed credentials to a required live user, never to another principal. Implement an explicit one-time legacy-subject mapping preserving tenant identity and reject unknown subjects. Test disabled/demoted static users, unknown legacy subject, multiple tenants and ordinary v2 epoch revocation. Coordinate the authoritative verifier with HTTP-01.

### SEC-03 — High / D — Historical saved dashboard password is ignored and its hash is not redacted

**Category:** authentication continuity and sensitive-data exposure. **Evidence tier:** code-confirmed — source-derived (direct evidence of schema/read mismatch).

- **R exact persisted shape:** `src/settings.rs:88–95,149–150` serializes **`auth.password_hash`** and `auth.password_changed_at`; there is no serde rename to `dashboard_password_hash`. `src/api/auth.rs:247–265,467–480` gives this stored verifier precedence over the environment password. `src/api/settings.rs:31–68` builds a public allowlisted response that excludes the whole `auth` object.
- **L:** `Core/LegacyHydrate.lean:232–240,433–438` reads only top-level **`dashboard_password_hash`**. `Core/Control.lean:1927–1946` uses that reader. `Core/LegacyHydrate.lean:218–230` preserves raw settings, but `Core/Control.lean:1255–1259` removes only top-level `password_hash` and selected Bitwarden spellings; `:5641–5665` returns remaining raw fields. It neither removes historical `auth.password_hash` nor top-level `dashboard_password_hash`. `Core/Store.lean:3529–3545` can verify Rust's colon PBKDF2 format, so this is not an unsupported PBKDF2 algorithm claim.
- **Failure scenario:** an operator changed the dashboard password under Rust while leaving the bootstrap environment password unchanged. After cutover, the saved password is not imported/read and the environment password becomes authoritative again; the revoked bootstrap password can regain access. A settings response also reveals the historical verifier to an authenticated admin/client that previously received no verifier, enabling offline guessing after token-only compromise. Admin-only GET is a qualification, not a claim of anonymous disclosure.
- **Migration-order qualification:** correcting the field spelling alone is insufficient. `Core/Store.lean:3646–3655` seeds an environment-derived hash first; the later importer at `Core/LegacyHydrate.lean:433–438` updates only an empty or placeholder hash, so an already-seeded environment hash would still block the historical saved verifier.
- **One-PR fix:** typed settings migration from `auth.password_hash`, ordered before environment seeding or using an explicit one-time atomic update of the correct bootstrap user's verifier, with authoritative stored-hash precedence. Return an explicit public settings DTO (not a growing blacklist), rejecting auth changes through generic settings patches. Round-trip an actual Rust JSON fixture and verify old bootstrap rejection, saved password acceptance and absence of all hash spellings in public responses. Coordinate rotation semantics with HTTP-01; do not count its existing fallback twice.

### SEC-04 — High / D — External secret grants lose requester-session identity (MCP-13 extension, not newly counted)

**Category:** cross-session secret authorization. **Evidence tier:** code-confirmed — source-derived (conditional on an existing approved Lean grant).

- **R:** `src/api/secret_broker.rs:48–74,295–313,334–355` stores a typed requester and checks `same_actor`; external sessions do not inherit mission-tree grants. `:1149–1164` revokes session grants. This is stricter than merely checking a mission string.

### SEC-06 — High / S,D — Approving secret write/delete/move discards the intended operation and grants read access instead

**Category:** security-sensitive effect/authorization mismatch. **Evidence tier:** code-confirmed — source-derived (direct evidence of missing effect).

- **R:** `src/api/secret_broker.rs:77–84,93–138` represents `read/write/delete/move`, pending encrypted values and move destination; `:942–1075` resolves the operation rather than treating every approval as a read. `:128–130,148–157` keeps pending ciphertext private.
- **L:** `Core/McpGateway.lean:1054–1060` funnels the four actions into `mcpSecretQueueAction`; `Core/SecretAndApproval.lean:359–387` writes `kind`, encrypted value, project and secret name but no move destination. Both batch (`:1021–1042`) and single approval (`:1122–1145`) always append a read-style grant and remove `encrypted_value`; neither decrypts the pending write nor invokes BWS create/edit/delete. The returned approved state is not a durable secret mutation.
- **Failure scenario:** a mission queues rotation of a credential or deletion/move from a sensitive vault project; the human approves it and sees approval success. The old secret remains active/in its old project, the proposed replacement value is discarded, and a read grant may be created that was not the requested effect. No assumption that the underlying third party revoked the old key is made.
- **One-PR fix:** use a typed action resolver shared by single and batch approvals. For write/delete/move perform exactly the requested BWS mutation, retain encrypted intent until durable outcome, record errors/uncertainty instead of approval success, and issue read grants only for read actions. Until implemented, reject unsupported action kinds before queueing. Preserve Rust key/project/destination/value-digest fields with real Rust fixtures.

### SEC-07 — High / D — Revoking a mission-access request leaves its independent live grant effective

**Category:** authorization revocation failure. **Evidence tier:** code-confirmed — source-derived (qualified to request-ID revocation path).

- **R:** `src/api/mission_access.rs:108–153,175–180` stores the live grant in the approved request itself; `:622–646` revokes that request. `live_grant` requires its approved state and expiry.
- **L:** `Core/SecretAndApproval.lean:1213–1246` allocates a **new grant UUID** but does not record that UUID in the approved request. `:1267–1280` revokes grants by the supplied ID and requests by that same ID. For the historical request-ID DELETE, only the request changes. `:187–196` authorizes reads exclusively from `grants`, ignoring request state.
- **Failure scenario:** approve request R, producing grant G; send the historical **`DELETE /api/mission-access/:id` with R's request ID**. The UI record becomes revoked and the API returns `{ok:true}`, but G remains active and subsequent cross-mission reads still pass. This uses the real historical route, not an invented `requests/:id` DELETE alias. **Revocation by the actual new G grant ID works.**
- **One-PR fix:** make the request/grant one authority record or persist an explicit immutable link and revoke it atomically in both directions. Preserve the historical request-ID route. Verify read denial immediately after request-ID and grant-ID revocation for single/batch approval and after reload.

### SEC-08 — High / M,D — Session-scoped privilege grants are evaluated as unconditional TTL leases

**Category:** privilege lifetime/revocation failure. **Evidence tier:** code-confirmed — source-derived (direct evidence of loss of liveness inputs; execution still needs a valid lease and caller).

- **R:** `src/api/privilege_broker.rs:765–781,803–831` persists `session_scoped` and `session_expires_at` and supplies mission-active/session-expiry to the kernel. `:1512–1526,1617–1661` implements session-grant reaping; `:2447–2450` rejects dead external sessions. The second reader traced asynchronous grace/reaping (`scope_reaper:114–144`): the comparison is **after that reap point**, not instantaneous revocation at mission termination.
- **L:** `Core/SecretAndApproval.lean:671–697,704–710` copies `session_scoped` only into JSON, not the lease. `Core/Store.lean:221,2451–2478` has no session subject, session expiry or session-scoped column. `Core/Control.lean:2039–2045` calls `privilegeStep sameOwner 1 ... now expires (expires + 3600)`: mission-active is hardcoded and session expiry is synthesized from TTL. **The verifier still requires an authorized admin caller and nonempty mission ID** (`:1979–1999`), along with matching lease/target/scope and command restrictions. The daemon calls Core using its API token (`Bin/PrivdMain.lean:239–290`); its TOCTOU checks do not restore the missing mission-liveness input.
- **Failure scenario:** a **nonempty-mission**, session-scoped lease remains within TTL after its requesting mission has ended and Rust's asynchronous grace/reaper would have revoked it. With a valid admin verifier caller and matching mission, target, scope and command restrictions, Lean's missing liveness check can still admit the lease until TTL unless explicitly revoked/bunkered. **An empty external-session grant cannot simply pass this verifier, and ordinary login/MCP session-token revocation is not bypassed.** No privileged execution is claimed.
- **One-PR fix:** add typed principal/session binding and real session expiry to the lease owner; query live mission/session at verification and revoke grants on terminal/revocation transitions. Fail closed when ownership/session linkage is unavailable. Test termination, external revocation, hard expiry and explicitly non-session-scoped TTL grants. Extend MCP-13's subject schema, not a second identity representation.

### SEC-09 — High / M — Persisted Rust Bunker state is not imported into the live enforcement source

**Category:** security-state migration failure. **Evidence tier:** code-confirmed — source-derived (qualified to cutover with nonzero historical bunker state).

- **R:** `src/api/privilege_broker.rs:948–964,1073–1074` stores `bunker_state` in `.sandboxed-sh/privilege_access.json` and derives current lockdown from it. `src/api/auth.rs:585–603` suspends external MCP sessions in HardLockdown.
- **L:** the new authority is `core_boot_state.bunker_state`, default **0** (`Core/Store.lean:223,2484–2495`). `Core/Control.lean:6368,6404` hydrates legacy state and then initializes the live ref from SQLite. The hydration function (`Core/LegacyHydrate.lean:422–438` onward) does not read `privilege_access.json`/its bunker state. The JSON is later read for requests/audit, not as lockdown authority (`Core/SecretAndApproval.lean:806,1287–1292`).
- **Failure scenario:** on a **cold cutover with legacy `bunker_state > 0` and new SQLite state 0**, Core initializes the live enforcement source to Normal even though the old persisted JSON still says lockdown. The persisted lockdown is lost at migration; no assumption that old privilege leases migrate successfully is needed. This is **not** a claim about whole-MCP-call lockdown parity or every external-session operation after cutover.
- **One-PR fix:** before serving requests, migrate valid historical bunker state under a monotonic maximum rule; fail closed on ambiguous/corrupt security-state input and durably mark migration. Keep one authority afterward. Verify cold cutover for states 0/1/2 and restart, without allowing stale JSON to undo a later explicit signed unbunker.

**Category:** rate/resource admission compatibility. **Evidence tier:** code-confirmed — source-derived (direct evidence of missing cap consumer; no latency/load experiment). This is not a newly demonstrated security exploit.
